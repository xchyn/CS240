Exercise set 10 · after the fractional binary lecture Fractions in binary

Numbers that are not whole

Place values on the right of the binary point; converting each half of a number with its own algorithm; the Fixed<w, b> notation; and IEEE 754 floating point — sign, exponent and mantissa, the bias, the hidden 1, and the patterns reserved for zero, infinity and NaN.

Every number in this course so far has been a whole one. Set 2 counted in various bases, Set 8 made some of them negative, and all of it stopped at the units place. Real computation does not: 3.14159, 2.71828, 1.41421.

There are two ways to store such a number, and the difference between them is simply where the point goes. Fix it in one place and you get fixed point, which is simple and limited. Let it move, and store where it went, and you get floating point — which is what every machine actually uses.

10.1Binary fractions

The place values continue to the right of the point exactly as you would guess. Each step left multiplies by two, so each step right divides by two:

place232221202−12−22−32−4
worth84210.50.250.1250.0625

and a number is read by adding up the places that hold a 1, on both sides of the point at once:

That is the whole of reading a binary fraction. The only new thing compared with Set 2 is that the places keep going.

Which fractions can be written exactly

Only those whose denominator is a power of two. A quarter is 0.01 and three eighths is 0.011, but one third and one fifth have expansions that repeat forever, exactly as one third does in decimal. Exercise 10.4 works one out, and the consequences run all the way to Exercise 10.29.

10.2Converting across the point

The rule that keeps this painless:

Split the number at the point and convert each half with its own algorithm, then put them back together.

Never try to convert the whole thing at once. The two halves use different procedures, and mixing them is the main way this goes wrong.

The integer part uses repeated division, exactly as in Set 2: divide by 2, record the remainder, repeat, and read the remainders bottom to top.

The fractional part uses repeated multiplication: multiply by 2, record the integer part of the result as the next bit, keep the leftover fraction, and repeat until the fraction becomes 0 or you have enough bits.

The digits come out in opposite orders

Repeated division produces the integer bits least significant first, so they must be reversed at the end.

Repeated multiplication produces the fraction bits most significant first — the first bit you get is the one immediately after the point. No reversing. Reversing them anyway is the single most common mistake on this topic.

Worked example

Convert 9.6875 to binary.

The integer part, 9, by repeated division: 9 → 4 r1, 4 → 2 r0, 2 → 1 r0, 1 → 0 r1 — reading the remainders bottom to top gives 1001.

The fractional part, 0.6875, by repeated multiplication:

=bitkeep
0.6875 × 21.37510.375
0.375 × 20.7500.75
0.75 × 21.510.5
0.5 × 2110 — stop

The fraction hit 0, so the expansion terminates. Reading the recorded bits downward — in the order they came out — gives 1011.

Putting the halves back together:

9.6875 = 1001.1011

Check it by place values: 8 + 1 + ½ + ⅛ + 1⁄16 = 9.6875.

Going the other way, from binary back to decimal, the place-value sum always works. The lecture's alternative processes the fraction bits right to left, starting from 0 and applying

Result ← (Result + digit) ÷ 2

once per bit. It needs no powers of two and is easier to do in your head; Exercise 10.5 runs it and checks it against the place-value sum.

10.3Fixed<w, b>

So far the point has been written on the page. A machine does not have that luxury — a register holds bits and nothing else. Fixed point is the agreement that the point sits in a particular place and everybody remembers where.

The notation
  • Fixed<w, b> means w bits in total, of which the rightmost b sit to the right of an implied binary point.
  • The value is the ordinary two’s complement integer divided by 2b.
  • The binary point is not stored anywhere. It exists only in the interpretation.

That last point is the one to hold on to. The same eight bits are a different number under a different agreement, and nothing in the bits says which agreement is in force — Exercise 10.6 reads one pattern three ways.

The payoff is that fixed-point arithmetic needs no new hardware. Two values with the same b can be added by the integer adder of Set 8, unchanged, and the result is correct in the same format. Exercise 10.11 subtracts two values that way and Exercise 10.12 is about why it works, and about what happens when the two bs differ.

Negative values need no new machinery either. The stored integer is two’s complement, so a negative fixed-point number is read, written and negated by exactly the rules of Set 8 — including the one value that cannot be negated. Exercises 10.8 to 10.11 work through all of it.

10.4Where fixed point runs out

Fixed point spends its bits at a fixed resolution across a fixed range, and the two pull against each other. In Fixed<8, 4> the smallest step is 1⁄16 and the largest value is just under 8. Moving the point right buys precision and loses range; moving it left does the reverse. With 8 bits you cannot have both.

Scientific notation is how people solve this on paper. Rather than writing 0.0000000000667, write 6.67 × 10−11 — a few significant digits, plus a separate exponent saying where the point belongs. The digits give precision and the exponent gives range, and they are stored separately so they do not compete.

Floating point is that idea in binary. Write the number as

1.xxxxxxx2 × 2yyyy

and store the two parts: the digits after the point, called the mantissa, and the exponent. Rewriting a number into this shape — one non-zero digit before the point — is called normalising it, and in binary that leading digit is always 1, which turns out to matter.

10.5IEEE 754

The standard that every processor follows is IEEE 754, from the Institute of Electrical and Electronics Engineers. It fixes how the three pieces are packed into a word.

The sign bit is 0 for positive and 1 for negative, and it is the sign of the whole number — this is not two’s complement, and negating a float means flipping one bit rather than complementing anything.

That one decision has consequences in every direction, which Exercises 10.17 to 10.19 and 10.24 pick apart: negation becomes free, the range becomes symmetric, zero acquires a second bit pattern, and comparison stops being a plain unsigned compare. Keep the two signs apart as you read on — the sign of the number lives in the sign bit, and the sign of the exponent is a separate matter handled by the bias below.

10.6The bias and the hidden 1

Two pieces of cleverness make the format work, and both are worth understanding rather than memorising.

The bias. Eight bits read as an ordinary binary number give 0 to 255, all non-negative — but exponents need to go negative, for numbers below 1. So the stored pattern is shifted:

stored pattern − 127 = the actual exponent

An exponent of 3 is stored as 130, and an exponent of −6 is stored as 121. For double precision the same trick uses a bias of 1023. Exercise 10.20 asks why a bias is used rather than, say, two’s complement in the exponent field.

The hidden 1. A normalised binary number always looks like 1.something — the leading digit cannot be 0, or it would not be normalised, and in binary the only other option is 1. A bit that is always the same carries no information, so it is not stored. The 23 stored bits are the ones after the point, and the leading 1 is put back when the number is read.

The mantissa field therefore holds 23 bits but delivers 24 bits of precision, which is a whole bit of accuracy for free. The values it can express run from 1.000… to 1.111…, that is from 1 up to just under 2.

10.7Special values

The hidden 1 creates a problem: if every number starts with an invisible 1, how do you write zero? It cannot be done — so two exponent patterns are reserved, and what they mean depends on the mantissa:

mantissa = 0mantissa ≠ 0
exponent all 0s±0subnormal (very close to 0)
exponent all 1s±∞NaN

An all-zero exponent with an all-zero mantissa is zero — and because the sign bit is separate, there are two of them, +0 and −0, which compare as equal. An all-ones exponent with an all-zero mantissa is infinity, which is what overflow and division by zero produce. And an all-ones exponent with anything else is NaN, Not a Number, the result of something genuinely undefined like 0 ÷ 0 or the square root of a negative.

The remaining corner, an all-zero exponent with a non-zero mantissa, is a subnormal number: the hidden 1 is taken to be 0 instead, which gives up precision in exchange for representing values even closer to zero.

10.8Reference

  • Place values right of the point: 1⁄2, 1⁄4, 1⁄8, 1⁄16…
  • Decimal to binary: integer part by repeated division, remainders read bottom to top; fraction part by repeated multiplication, bits read top to bottom.
  • Fixed<w, b>: w bits total, b after an implied point; value = two’s complement integer ÷ 2b; the point is never stored. Range −2w−1⁄2b to (2w−1 − 1)⁄2b — asymmetric, as in Set 8.
  • Negating: in fixed point, flip all w bits and add 1 (the most negative value returns itself); in IEEE 754, flip the sign bit alone.
  • IEEE 754 single: 1 sign + 8 exponent (bias 127) + 23 mantissa = 32 bits, 24 bits of precision.
  • IEEE 754 double: 1 + 11 (bias 1023) + 52 = 64 bits, 53 bits of precision.
  • Value of a normal number: (−1)sign × 1.mantissa × 2(exponent field − bias).
  • Reserved: exponent all 0s → zero or subnormal; all 1s → infinity or NaN.

10.9Exercises

Keep the two halves of a number separate on the page, and label which algorithm you are running. Most errors here are not arithmetic — they are a reversed fraction or a division where a multiplication belonged.

Binary fractions

Convert these to decimal: 0.1101, 1010.011, 0.0001.

Add up the places that hold a 1.

0.1101 has 1s in the 1⁄2, 1⁄4 and 1⁄16 places: 0.5 + 0.25 + 0.0625 = 0.8125.

1010.011 splits at the point. The integer part 1010 is 8 + 2 = 10; the fraction 011 is 0.25 + 0.125 = 0.375. Together 10.375.

0.0001 has a single 1 in the 1⁄16 place: 0.0625.

Two habits worth forming. A binary fraction is always a sum of distinct powers of one half, so the answer is always a multiple of the smallest place shown — here a multiple of 1⁄16, which 0.8125 and 0.0625 both are. And the value of 0.xxxx is always less than 1, so if your answer exceeds 1 you have read a place wrongly.

The order is the thing to be careful about. The first bit produced is the first bit after the point — the 1⁄2 place. Writing the bits in the order they appear is correct; reversing them, as you would for the integer half, produces a different and wrong number.

Notice the two halves never interact. The division chain knows nothing about the fraction and the multiplication chain knows nothing about the integer — which is exactly why the rule says to split first. A single procedure attempting both at once has no well-defined thing to do with the carry between them.

Convert 0.2 to binary. What happens, and what does it tell you about which decimal fractions can be stored exactly?

Repeated multiplication:

=bitkeep
0.2 × 20.400.4
0.4 × 20.800.8
0.8 × 21.610.6
0.6 × 21.210.2
………back to 0.2 — it repeats

The fraction 0.2 has come back, so the whole block repeats forever:

0.2 = 0.0011 0011 0011 0011…

The pattern 0011 repeats without end, exactly as 1⁄3 = 0.333… does in decimal.

Which fractions terminate. A fraction terminates in binary exactly when, in lowest terms, its denominator is a power of two. One fifth is 1⁄5 and 5 is not a power of two, so it cannot. The same test in decimal asks for a denominator built from 2s and 5s, which is why 1⁄5 is fine in decimal and 1⁄3 is not.

The consequence. Any binary format with finitely many bits must cut this expansion off somewhere, so 0.2 is never stored exactly — not in fixed point, not in floating point, not in any width. What is stored is the nearest representable value, which is close but not equal.

That is not a defect of a particular machine; it follows from the choice of base. And it is the root of the behaviour in Exercise 10.29, which you may already have run into when a program printed something ending in …0004.

Convert 0.1011 to decimal using the lecture’s right-to-left method, Result ← (Result + digit) ÷ 2, then check with place values.

Take the fraction bits right to left — 1, 1, 0, 1 — starting with Result = 0:

takingcomputeResult
digit 1(previous + 1) ÷ 20.5
digit 1(previous + 1) ÷ 20.75
digit 0(previous + 0) ÷ 20.375
digit 1(previous + 1) ÷ 20.6875

so 0.1011 = 0.6875.

Check by place values: ½ + ⅛ + 1⁄16 = 0.6875. They agree.

Why it works. Each division by 2 shifts everything one place right, making room for the bit that is one place more significant. Running right to left means the earliest bit gets divided the most times, ending up with the smallest weight — which is right, since it is the least significant.

The practical advantage is that it needs no powers of two and no addition of fractions: just halve, add a bit, halve again. For a long mantissa it is considerably less error-prone than summing eight separate place values.

Fixed point

The eight bits 10110100 are read as Fixed<8, 0>, then Fixed<8, 3>, then Fixed<8, 8>. Give the three values.

In every case the bits are first read as an ordinary two’s complement 8-bit integer. The leading bit is 1, so the value is negative: 10110100 as an integer is −76.

Then divide by 2b:

read asvaluedecimal
Fixed<8, 0>−76 ÷ 20−76
Fixed<8, 3>−76 ÷ 23−9.5
Fixed<8, 8>−76 ÷ 28−0.296875

Same bits, three different numbers — and nothing in the bits distinguishes the cases. The format has to be known from elsewhere: the type of the variable, the specification of the hardware, the agreement between the two ends of a wire.

The pattern is worth noticing. Increasing b by one halves the value, because the point has moved one place left over bits that did not move at all. A fixed-point “conversion” between scalings is therefore a shift, not a computation.

For signed Fixed<8, 4>: what is the smallest step between values, what are the largest and smallest numbers representable, and how many distinct values are there?

The underlying integer is an 8-bit two’s complement number, so it runs from −128 to 127, and every value is that integer divided by 24 = 16.

The step is one unit in the last place: 1⁄16 = 0.0625. Nothing between two adjacent values can be represented.

The range is −128⁄16 to 127⁄16, that is −8 to 7.9375 — the same asymmetry as Set 8’s integer range, for the same reason.

How many values: 256, one per bit pattern. That number does not change with b, which is the whole point of the trade: 8 bits give 256 values and b decides only where they are placed. With b = 0 they are spread one apart from −128 to 127; with b = 8 they are packed 1⁄256 apart between −0.5 and just under 0.5.

That fixed spacing is what distinguishes fixed point from floating point. Here the gap between neighbours is the same everywhere; in floating point it grows with the size of the number, which Exercise 10.28 takes up.

Negative values in fixed point

Everything in this group rests on one sentence: a Fixed<w, b> number is a w-bit two’s complement integer, and the point is something you say about it rather than something stored. So every rule from Set 8 survives unchanged — and so does every trap.

What is 11110110 as Fixed<8, 2>? Show the two’s complement step explicitly.

The leading bit is 1, so this is negative. Negate it to find the magnitude: flip 11110110 to 00001001, add 1, giving 00001010 = 10. So the integer is −10.

Divide by 22 = 4:

−10 ÷ 4 = −2.5

The shortcut, if you prefer: write the bits with the point in place, 111101.10, and read the leading bit with its negative weight — −32 here, since it is the 25 place once the point has moved two positions. Then −32 + 16 + 8 + 4 + 1 + ½ = −2.5, which agrees.

Both routes work; the first is safer when you are tired, because it reuses the negation rule you already trust from Set 8 rather than asking you to work out the weight of the sign bit under an arbitrary scaling.

Encode −6.375 as Fixed<8, 3>. Give the eight bits.

Work with the magnitude first and negate at the very end. Doing it the other way round — negating the integer half and the fraction half separately — is the standard way to get this wrong.

Step 1, the magnitude in binary. 6.375 is 00110.011: the integer part and the fraction part by the two methods of Exercise 10.3.

Step 2, scale it to an integer. Fixed<8, 3> stores the value times 23 = 8, so the stored integer for the magnitude is

6.375 × 8 = 51 = 00110011

Notice that 00110011 is 00110.011 with the point rubbed out. Scaling by a power of two never changes a single bit; it only changes where you claim the point is.

Step 3, negate the whole eight bits. Flip 00110011 to 11001100 and add 1:

−6.375 = 11001101

Check by running Exercise 10.8 backwards: the leading bit is 1, so negate 11001101 to recover 51, and 51 ÷ 8 = 6.375. With the sign restored, −6.375. ✓

With the point written in, the pattern is 11001.101 — but nothing in the hardware holds that point, and the same eight bits under a different b are a different number, exactly as in Exercise 10.6.

Check the range first

Fixed<8, 3> runs from −16 to 15.875, so −6.375 fits. A value outside that range cannot be encoded at all, and the scaling step will quietly produce an integer that does not fit in eight bits — which looks like an answer but is not one.

In Fixed<8, 3>, what value is 10000000? Now negate it, and say what happens. What does this say about the range?

The value. 10000000 is the most negative 8-bit two’s complement integer, −128, so as Fixed<8, 3> it is

−128 ÷ 8 = −16

Negating it. Flip 10000000 to 01111111, add 1, and the carry runs the whole way along:

01111111 + 1 = 10000000

You get the same pattern back. Negation has failed — and it has failed silently, which is the dangerous part.

Why. The answer would be +16, which needs a stored integer of +128, and an 8-bit two’s complement integer stops at 127. So the positive counterpart of −16 is simply not in the format: the largest value is 15.875, one step short.

The range is asymmetric — −16 to 15.875, with one more negative value than positive. This is exactly the asymmetry of Set 8, because it is the asymmetry of Set 8: scaling by 2−3 multiplies both ends by the same factor and cannot make a lopsided range symmetric.

The practical rule: whenever you negate or subtract in fixed point, the most negative value is a special case, and code that negates a user-supplied value has to test for it. Floating point does not have this problem — Exercise 10.26 shows why.

Fixed-point arithmetic

Compute 3.25 − 5.5 in Fixed<8, 4> using an ordinary 8-bit integer adder and nothing else. Check the result.

The adder cannot subtract, so do what Set 8 did: add the negation. And do not convert anything to decimal along the way — the whole claim being tested is that the integer hardware needs no help.

Scale both operands. Fixed<8, 4> multiplies by 16, so 3.25 is stored as 52 = 00110100 and 5.5 as 88 = 01011000.

Negate the second. Flip 01011000 to 10100111, add 1, giving 10101000.

Three things the adder did not do: it did not look at the point, it did not know which bits were fractional, and it did not treat the negative operand differently from the positive one. That is the entire argument for fixed point.

Overflow

The carry out of the top bit was 0 and is discarded — in two’s complement it is not an error indicator. The real test, from Set 8, is the sign: here a positive and a negative operand were added, and that combination can never overflow, since the result lies between them. Overflow is possible only when both operands share a sign, and in fixed point it means the same thing it always did — the true answer is outside −8 to 7.9375.

Two Fixed<16, 8> values are added using an ordinary 16-bit integer adder, with no changes. Explain why the answer is correct. What goes wrong if one value is Fixed<16, 8> and the other Fixed<16, 4>?

Why it works. Write the two values as p⁄28 and q⁄28, where p and q are the stored integers. Their sum is

p⁄28 + q⁄28 = (p + q)⁄28

so adding the stored integers and interpreting the result with the same b gives exactly the right value. The common factor 2−8 comes out of the sum, and the adder never needs to know it is there.

This is the practical attraction of fixed point. No new hardware, no new instructions — a fixed-point add is an integer add, and so is a subtract.

Mixed scalings break it. With p⁄28 and q⁄24 there is no common factor to extract, and p + q means nothing: the adder lines up bit 0 with bit 0, but those bits are worth 1⁄256 in one operand and 1⁄16 in the other. It is adding sixteenths to two-hundred- fifty-sixths as though they were the same unit.

The fix is to rescale first: shift the Fixed<16, 4> value left by 4 so both are Fixed<16, 8>, then add. Which is the same discipline as keeping units straight in physics, and it is enforced by nothing but the programmer’s care — the bits will not complain.

Multiplication is different again: multiplying Fixed<w, b> by Fixed<w, b> gives a result scaled by 22b, so the product has to be shifted right by b to get back into the original format.

Floating point

Normalise these into the form 1.xxx × 2e: 1011.01, 0.000110, 1.1101.

Normalising means sliding the point until exactly one 1 sits to its left, and counting how far it moved. Moving left is a positive exponent; moving right is a negative one.

1011.01 — the point moves 3 places left: 1.01101 × 23.

0.000110 — the first 1 is four places after the point, so the point moves 4 places right: 1.10 × 2−4.

1.1101 is already normalised: 1.1101 × 20.

Check one by value. 1011.01 is 11.25, and 1.01101 is 1.40625, and 1.40625 × 8 = 11.25.

Two things to carry into the next exercises. The digits never change when you normalise — only the position of the point and the exponent — so the mantissa is just the original bit string with its leading zeros and its point removed. And every normalised number begins with 1, which is what makes the hidden bit possible.

Convert 6.5 to IEEE 754 single precision. Give the 32 bits.

Write it in binary. 6.5 = 110.1.

Normalise. 110.1 = 1.101 × 22.

Sign. Positive, so 0.

Exponent. The actual exponent is 2, and the field stores it biased: 2 + 127 = 129 = 10000001.

Mantissa. The bits after the leading 1 are 101, padded with zeros to 23 bits.

0 10000001 1010 0000 0000 0000 0000 000

The leading 1 of 1.101 is nowhere in the stored pattern, which is correct — it is the hidden bit, and putting it in the mantissa field is the commonest error on this conversion.

Convert 40.75 and −0.375 to IEEE 754 single precision. The second has a negative exponent.

40.75. In binary, 101000.11, which normalises to 1.0100011 × 25. Sign 0; exponent field 5 + 127 = 132 = 10000100; mantissa 0100011 padded to 23 bits.

0 10000100 0100 0110 0000 0000 0000 000

−0.375. The magnitude is 0.375 = 0.011, whose first 1 sits 2 places after the point, so it normalises to 1.1 × 2−2.

Sign is 1, since the number is negative. The exponent field is −2 + 127 = 125 = 01111101 — still a perfectly ordinary non-negative pattern, which is exactly what the bias is for.

1 01111101 1000 0000 0000 0000 0000 000

Note that the sign bit is the only difference between this and the encoding of +0.375. Floating point does not use two’s complement, so negating a number never touches the exponent or the mantissa.

Convert −45.25 and −0.40625 to IEEE 754 single precision.

Both are negative, and in both cases the sign is dealt with first and separately: set the sign bit, then forget the sign entirely and encode the magnitude. Nothing else in the format knows about it.

−45.25. The magnitude 45.25 is 101101.01, which normalises to 1.0110101 × 25 — the point moves 5 places left.

Sign 1. Exponent field 5 + 127 = 132 = 10000100. Mantissa 0110101, padded to 23 bits.

1 10000100 0110 1010 0000 0000 0000 000

−0.40625. The magnitude 0.40625 is 0.01101. Its first 1 lies 2 places after the point, so the point moves 2 places right and the exponent is −2: 1.101 × 2−2.

Sign 1. Exponent field −2 + 127 = 125 = 01111101. Mantissa 101, padded to 23 bits.

1 01111101 1010 0000 0000 0000 0000 000

Two signs, and they are unrelated. −0.40625 is a negative number with a negative exponent, and the two facts live in different fields: the sign bit says negative, the exponent field 01111101 is a perfectly ordinary positive pattern that happens to be below 127. A number can be negative with a positive exponent (−45.25), positive with a negative exponent (as in Exercise 10.13), or either combination of the two. Confusing them is the most common error on this page.

The bias is not two’s complement

The exponent −2 is stored as 125, not as a two’s complement −2. You add 127 and write the result as a plain unsigned 8-bit number — no flipping, no adding 1. Exercise 10.20 is about why the format was built this way.

Negative values in floating point

Floating point does not use two’s complement. The sign lives in one bit and the magnitude in the other 31, so negation is a single bit flip and nothing else moves. That one design choice is behind everything in this group — the good parts and the two awkward ones.

Decode this single-precision pattern: 1 10000010 1010 1000 0000 0000 0000 000

Split the fields. Sign 1, exponent 10000010, mantissa 10101000000000000000000.

Sign. 1, so the number is negative.

Exponent. 10000010 as an ordinary binary number is 130, and the actual exponent is 130 − 127 = 3.

Mantissa. Put the hidden 1 back: 1.10101.

−1.10101 × 23 = −1101.01 = −13.25

Multiplying by 23 moves the point 3 places right, which is why the shifted form appears directly. Reading it off: 8 + 4 + 1 + ¼ = 13.25.

A check that costs nothing: the exponent field was neither all 0s nor all 1s, so this is an ordinary normal number and the hidden 1 really is a 1. Had the field been all zeros, the rules of §10.7 would apply instead.

Decode this single-precision pattern: 1 01111100 0110 0000 0000 0000 0000 000

Split the fields. Sign 1, exponent 01111100, mantissa 01100000000000000000000.

Sign 1: negative.

Exponent. 01111100 is 124 as an unsigned binary number, so the actual exponent is 124 − 127 = −3. The field is smaller than 127, which is how a biased field says “negative exponent”.

Mantissa. Restore the hidden 1: 1.011.

Put it together. Multiplying by 2−3 moves the point 3 places right, so leading zeros appear:

−1.011 × 2−3 = −0.001011 = −0.171875

Reading the places: ⅛ + 1⁄32 + 1⁄64 = 0.171875, and the sign bit makes it −0.171875.

Two negatives, two meanings. This number is negative and has a negative exponent, and the two are independent facts read from different fields. Compare the pattern in Exercise 10.17: also negative, but with a positive exponent, so its point moved left and it is a number larger than 1 in magnitude. The sign bit tells you which side of zero; the exponent tells you how far from zero.

A sanity check worth doing every time

If the exponent field is below 01111111 (127), the magnitude is less than 1. If it is above, the magnitude is more than 1. Here the field is 124, so the answer had to come out as a fraction — and it did. An answer of −11 would have failed this check instantly.

Here is 7.25 in single precision: 0 10000001 1101 0000 0000 0000 0000 000. Write down −7.25 without redoing any of the conversion. Then compare with how Set 8 negates an integer: which system makes negation cheaper, and what does each pay for it?

Flip the sign bit. That is the whole answer.

7.25  =  0 10000001 1101 0000 0000 0000 0000 000
−7.25  =  1 10000001 1101 0000 0000 0000 0000 000

The exponent field 10000001 and the mantissa 1101… are untouched, because they describe the magnitude and the magnitude did not change. This is sign-and-magnitude, and it is what IEEE 754 uses for the sign — not two’s complement.

Set 8 negates differently. To negate an 8-bit two’s complement integer you flip all eight bits and add 1, and the carry can propagate the whole way along. Every bit may change, and the operation needs an adder.

Which is cheaper. Floating point, by a wide margin: one inverter on one wire, constant time, no carry, and it works on every value without exception — including zero, infinity and NaN.

And the symmetry that Exercise 10.10 found missing in fixed point is bought with a second zero, which Exercise 10.24 takes up.

Inside the format

The exponent field stores the exponent plus 127 rather than the exponent itself. Why bias it, rather than storing it in two’s complement? What range of actual exponents does an 8-bit field with bias 127 give, once the reserved patterns are removed?

Why a bias. Because it makes floating-point numbers compare in the same order as the integers with the same bit patterns. With a biased exponent, a larger number has a larger exponent field, which has a larger unsigned value — so for positive floats, comparing the 32 bits as if they were an unsigned integer gives the right answer. Hardware can sort or compare floats with integer circuitry.

Two’s complement would break that. A small negative exponent would begin with a 1 bit and so would look larger than a big positive exponent, and every comparison would need special handling.

The range. The field holds 0 to 255, which would give exponents −127 to +128. But both ends are reserved — 00000000 for zero and subnormals, 11111111 for infinity and NaN — so the usable field values are 1 to 254, giving actual exponents

−126 to +127

which is where the familiar limits of about 10±38 come from.

For double precision the same reasoning with 11 bits and bias 1023 gives exponents −1022 to +1023, and a range of roughly 10±308.

Exercise 10.20 claimed the bias lets floats be compared as though their bits were unsigned integers. Test the claim on 1, 2, −1 and −2 by reading each 32-bit pattern as an unsigned integer. Where does it hold, where does it fail, and what has to be done about it?

Encode the four, and read the same bits a second time as a plain unsigned integer:

value32 bitsas an unsigned integer
10 01111111 0000 0000 0000 0000 0000 0001,065,353,216
20 10000000 0000 0000 0000 0000 0000 0001,073,741,824
−11 01111111 0000 0000 0000 0000 0000 0003,212,836,864
−21 10000000 0000 0000 0000 0000 0000 0003,221,225,472

Among the positives it works. 1 < 2 as numbers, and 1,065,353,216 < 1,073,741,824 as unsigned integers. The exponent field sits immediately below the sign bit and is biased, so a bigger number has a bigger field; where the fields tie, the mantissa decides, and it too is read in the right order. That is exactly what the bias was for.

Among the negatives it reverses. −2 < −1 as numbers, but 3,221,225,472 > 3,212,836,864 as unsigned integers — the comparison comes out backwards. The reason is the same one that makes the negation of Exercise 10.19 cheap: the magnitude bits do not know about the sign. A larger magnitude is a larger unsigned reading whichever side of zero the number is on, so the ordering of the negatives is a mirror image of what it should be.

And every negative outranks every positive, since the sign bit is the most significant bit of the pattern: all four negative readings exceed all four positive ones. This is sign-and-magnitude behaving exactly as Set 8 warned sign-and-magnitude behaves, and it is precisely the defect two’s complement was invented to cure.

What to do about it. The fields themselves are fine; only the sign needs repairing. The standard fix is two cases, each a handful of gates:

  • sign bit 0 (positive): set the top bit to 1;
  • sign bit 1 (negative): invert all 32 bits.

After that transformation an ordinary unsigned comparison is correct across the whole range, negatives below positives and each group in the right order. Inverting is what undoes the mirror, and setting the top bit lifts the positives above the negatives.

So the claim is better stated as: the bias makes the magnitude of a float compare as an unsigned integer, and the sign is handled separately — which is one more entry for the table in Exercise 10.19. The one case this still gets wrong is −0, which has a different pattern from +0 but must compare equal to it; see Exercise 10.24.

The mantissa field is 23 bits but the format is said to give 24 bits of precision. Explain. Which number cannot be normalised, and how does the format cope?

The 24th bit. A normalised binary number is 1.something — the digit before the point is always 1, because it cannot be 0 (that is what normalised means) and binary has no other option. A value that never changes carries no information, so it is not stored: the 23 bits hold what comes after the point, and the leading 1 is supplied when the number is read.

So the significand actually in play is 24 bits wide while only 23 are kept — one bit of precision for free, which doubles the number of distinct values at no cost in storage.

The number that cannot be normalised is zero. It has no leading 1 to slide the point in front of; no exponent makes 0 look like 1.something.

How the format copes: by reserving a pattern instead of computing one. An exponent field of all zeros with an all-zero mantissa means zero, by decree. This is why §10.7 exists at all — the hidden bit is what makes the format efficient and also what makes zero a special case.

The same reservation is what gives two zeros, +0 and −0, since the sign bit is independent and both settings are legal. The standard requires them to compare equal despite having different bit patterns, which is the one place where comparing floats as integers goes wrong.

The first two are the two zeros. The next two are the infinities — produced by overflow, or by dividing a non-zero number by zero, and they behave sensibly in arithmetic: 1 ÷ ∞ is 0.

The fifth has an all-zero exponent but a non-zero mantissa, so it is a subnormal: the hidden bit is taken as 0 rather than 1, giving a number much closer to zero than any normal value, at the cost of fewer significant bits.

The last has an all-ones exponent with a non-zero mantissa, so it is NaN. NaN is what an operation returns when there is no right answer at all — 0 ÷ 0, ∞ − ∞, the square root of a negative number. Its defining property is that it compares unequal to everything, including itself, which is the standard trick for testing whether a value is NaN.

The thing to take away is that the exponent field is checked first. All zeros and all ones are not exponents; they are flags, and only the 254 patterns between them describe ordinary numbers.

Two of the patterns in Exercise 10.23 are zero. Why does the format have two zeros rather than one? Which operations produce the negative one, and how do the two behave?

Why there are two. Zero is signalled by a reserved combination — exponent field all 0s with mantissa all 0s — and that reservation says nothing about the sign bit, which is a separate bit that is free to be either value. Both settings are legal patterns, so both exist:

0 00000000 0000 0000 0000 0000 0000 000 = +0
1 00000000 0000 0000 0000 0000 0000 000 = −0

This is the price of the cheap negation in Exercise 10.19. Sign-and-magnitude spends one pattern twice on zero; two’s complement spends the spare pattern on an extra negative value instead, which is why Set 8’s range is asymmetric and this one is not.

Where −0 comes from. Negating zero, as Exercise 10.19 does — flip the sign bit of +0. Multiplying or dividing when exactly one operand is negative and the result is zero: −1 × 0. And underflow: a negative result too small in magnitude for even a subnormal rounds to −0, which preserves the information that the true answer was below zero.

How they behave. The standard requires +0 == −0 to be true, so no comparison can tell them apart, even though the 32 bits differ. But they are not interchangeable:

1 ÷ (+0) = +∞   but   1 ÷ (−0) = −∞

so a sign that compares equal can still flip the sign of a later result. That is the practical reason to care, and it is why the sign is kept rather than discarded.

It is also the one place where the comparison trick of Exercise 10.21 breaks: the transformation there maps the two zeros to different values, so an unsigned compare calls them unequal while the standard calls them equal. Hardware comparators special-case it.

The other side of the same coin

NaN compares unequal to everything including itself, and the zeros compare equal despite differing in their bits. Equality of floats and equality of bit patterns are two different relations, and only one of them is what a program usually means.

What are the largest and the smallest positive normal single-precision values? Give the bit patterns and roughly their decimal size.

The largest. Take the biggest usable exponent field, 11111110 = 254, so the exponent is 127, and the biggest mantissa, all 1s:

0 11111110 1111 1111 1111 1111 1111 111

which is just under 2 × 2127 = 2128, or about 3.4 × 1038. Anything larger overflows to infinity.

The smallest positive normal. Take the smallest usable exponent field, 00000001 = 1, so the exponent is −126, and a zero mantissa, which means a significand of exactly 1:

0 00000001 0000 0000 0000 0000 0000 000

which is 2−126, about 1.2 × 10−38.

Note that the exponent fields used are 254 and 1, not 255 and 0 — both extremes are reserved, as Exercise 10.20 established. Using them would give infinity and zero rather than very large and very small numbers.

Below the smallest normal there are still the subnormals, which fill the gap down to about 10−45 with steadily fewer significant bits. Without them there would be a jump straight from 1.2 × 10−38 to zero, and the difference of two distinct numbers could come out as exactly 0.

What is the most negative single-precision value — the finite value furthest below zero? Give its bit pattern. Is the single-precision range asymmetric, as Set 8’s was?

The pattern. Take the largest finite value from Exercise 10.25 and set the sign bit:

1 11111110 1111 1111 1111 1111 1111 111

which is −3.4 × 1038 — the same magnitude as the largest positive, carrying a minus sign. Anything further from zero overflows to −∞, 1 11111111 0000 0000 0000 0000 0000 000.

The range is symmetric. Every finite single-precision value has a finite negative counterpart with the identical exponent and mantissa, because negation touches only the sign bit (Exercise 10.19) and the magnitude bits have no idea it happened. There is no value that cannot be negated.

Contrast Set 8, and Exercise 10.10. In 8-bit two’s complement the range is −128 to 127: −128 has no positive counterpart, and negating it silently returns itself. Fixed<8, 3> inherits that exactly, scaled — −16 to 15.875. Floating point simply does not have the problem.

What the symmetry cost. Count the patterns. Two’s complement uses all 256 of its 8-bit patterns for 256 distinct values. Sign-and-magnitude spends two patterns on zero (Exercise 10.24), so it has one fewer distinct value than patterns — and that is where the extra negative value went. The two formats make opposite choices with the same spare pattern:

spare pattern spent onresult
an extra negative value (two’s complement)unique zero, asymmetric range, negation can fail
a second zero (IEEE 754)symmetric range, negation never fails, two zeros to reason about

Neither is a mistake. Two’s complement is built so that one adder serves both signs, which matters for integers; IEEE 754 is built so that magnitude and sign stay separate, which matters when the magnitude already has two fields of its own.

Give the field widths, the bias and the precision of IEEE 754 double precision, and work out roughly how many decimal digits it is good for.

The fields: 1 sign bit, 11 exponent bits with a bias of 1023, and 52 mantissa bits, for 64 in total.

The precision is 53 bits — the 52 stored plus the hidden 1, by the same argument as Exercise 10.22.

In decimal digits. Each decimal digit needs about log2 10 ≈ 3.32 bits, so

53 ÷ 3.32 ≈ 16 digits

which is why a double prints about 15 to 17 significant figures before it starts inventing. Single precision, with 24 bits, gives 24 ÷ 3.32 ≈ 7 digits — and that is the practical reason doubles are the default in most languages: seven digits is not many once a few operations have each rounded.

The exponent range follows the same pattern as Exercise 10.20: field values 1 to 2046, so exponents −1022 to +1023, giving magnitudes up to about 10308.

Two consecutive single-precision numbers differ by one unit in the last place of the mantissa. How far apart are consecutive floats near 1, and near 1000? Why does this make floating point unlike fixed point?

Changing the last mantissa bit changes the significand by 2−23, and the whole value is the significand times 2e, so the gap between neighbours is 2e−23 — it depends on the exponent.

Near 1 the exponent is 0, so the gap is 2−23 ≈ 1.2 × 10−7. That quantity is called the machine epsilon.

Near 1000 the exponent is 9, since 29 = 512 and 210 = 1024, so the gap is 2−14 ≈ 6.1 × 10−5 — about 500 times larger.

The contrast with fixed point. In Fixed<8, 4> the step is 1⁄16 everywhere, near zero and at the top of the range alike. Floating point instead keeps a constant relative precision — about seven significant digits whatever the magnitude — by letting the absolute gap grow with the number.

That is the right trade for scientific work, where what matters is the number of significant figures rather than the absolute error. It is the wrong trade for money, where an error of a cent matters just as much on a large balance as a small one — which is why financial software uses fixed point or decimal types rather than floats.

It also explains a result that surprises people: adding a small number to a large one can change nothing at all. If the gap at that magnitude exceeds what you are adding, the exact answer rounds back to where it started.

Challenge. In most programming languages 0.1 + 0.2 does not equal 0.3. Explain exactly why, using everything in this set. Then say what a program should do instead of testing two floating-point values for equality.

Set 2 promised this one would come back. Here it is.

Neither operand is stored exactly. By Exercise 10.4, 1⁄10 has a repeating binary expansion, so 0.1 cannot be represented in any finite number of bits; neither can 0.2, nor 0.3. What gets stored in each case is the nearest representable double.

The nearest double to 0.1 is not 0.1 but

0.1000000000000000055511151231257827021182

and the nearest to 0.2 is exactly twice that, since doubling only changes the exponent. So the two stored values carry small errors in the same direction.

The sum is then rounded again. Adding the two stored values gives a number that itself needs rounding to the nearest double, and the result of that rounding is

0.3000000000000000444089209850062616169453

whereas the nearest double to 0.3 is

0.2999999999999999888977697537484345957637

Different values, differing in the last bit — so the comparison is false, and printing the sum with enough digits shows 0.30000000000000004.

Nothing here is a bug. Every step did the best it could: each rounding was to the nearest representable value, and the standard guarantees exactly that. The errors are tiny and they simply did not cancel.

What to do instead. Do not test floating-point values for equality. Test whether they are close enough:

if (fabs(x - y) < tolerance)

with a tolerance chosen for the problem — and, by Exercise 10.28, a tolerance that is relative to the size of the numbers rather than absolute, since the gap between neighbouring floats grows with magnitude. A tolerance of 10−9 is strict near 1 and meaningless near 1012.

Where this bites in practice

Two places, both common. Accumulating money in floating point and finding the total off by a fraction of a cent — use fixed point, or integer counts of cents. And looping with a floating-point counter, for (x = 0; x != 1.0; x += 0.1), which never terminates because the accumulated value steps straight over 1.0. Count with an integer and multiply.
